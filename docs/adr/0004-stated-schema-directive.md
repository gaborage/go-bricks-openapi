# A `schema` type directive states the wire schema of a Marshaler type the project declares

A Marshaler type the project declares is documented as `{}` with a warning in every body position unless it encodes as text both ways (ADR 0002), and that warning feeds `--strict` with no way to silence it short of `json:"-"`, which cannot reach a payload or a request type. We will let the project state the type's wire schema once, with `//openapi:schema <type> [<format>]` in the doc comment of its package-level type declaration. It will be the first type Directive: each directive name has exactly one placement (see **Directive** in `CONTEXT.md`), so `schema` will live on the type, while the route directives (`public`, `errors`, `meta`) are attached to a route registration. The Stated schema is one schema for both directions, trusted as written, and it will replace ADR 0002's "There is no per-field override yet" for Marshaler types the project declares. Decided while triaging #117, together with #113 for pointer receivers.

- **Arguments.** `<type>` is `string`, `integer`, `number` or `boolean`; `<format>` is optional and free-form, copied verbatim. Anything else warns and the directive is ignored, so a type that writes an object stays `{}`. `object` is not accepted, because a bare `{type: object}` would silence the warning without describing anything; `array` never is, because OAS 3.0 requires `items`.
- **Which types.** Only Marshaler types the project declares. On a type that is not a Marshaler type the directive warns "has no effect". A type that encodes as text both ways accepts only `string [<format>]`; any other type word warns. The directive does not apply to a type with any encode-side method (`MarshalJSON`, `MarshalJSONTo`, `MarshalText` or `AppendText`, declared or promoted) outside its value method set: it warns, naming the method and suggesting a value receiver, and the type stays `{}` with its Marshaler warning. `encoding/json` calls a pointer-receiver method only where the value is addressable, so one Stated schema would be wrong at some positions, such as a map value or a payload returned by value. Applying it only at explicit `*T` positions, where the value is addressable, would be correct there, but it belongs with a general `*T` rule for in-module types with pointer-receiver marshal methods, which would change their existing output and is left to its own issue (ADR 0002, as amended).
- **Generic types.** A directive on a generic type declaration (`type Opt[T any] struct{ … }`) does not apply: it warns "has no effect", and its Instantiations are documented as they would be without the directive. This holds whichever of #114 and #117 lands first. A generic Marshaler type's wire form usually depends on its type argument (an `Opt[T]` whose `MarshalJSON` writes its `T` is a number as `Opt[int]` and a string as `Opt[string]`), so one Stated schema cannot describe every Instantiation.
- **Output.** The Stated schema is emitted inline, with no component, in every JSON body position: field, slice item, map value, nested container, payload and request body. A pointer field adds `nullable: true`; a `Result[*T]` payload does not, matching `Result[*string]`. When a route's request type has a Stated schema, the requestBody's schema is the Stated schema; a request whose every field is a path, query or header parameter still has no body. The type's Marshaler warning is not raised, and a route counts as typed when its request type or its `Result[T]` payload has a Stated schema.
- **Keywords.** `validate` keywords are dropped, as for every Marshaler type; an enclosing slice's or map's cardinality and `required` membership are kept. `example:` is converted to the stated type, and dropped if it has no valid form in it.
- **Untouched.** Path, query and header parameters (bound by kind) and JOSE routes.
- **Inheritance.** A plain alias (`type MA = Money`, with no marshal method of its own) uses `Money`'s Stated schema, and a directive on `MA` itself warns "has no effect, state it on Money". A defined type (`type M2 Money`) does not inherit, since it drops `Money`'s methods. A promoting struct (`type W struct{ Money }`) does not inherit either: `W` is its own Marshaler type and takes its own directive.
- **Alias receiver.** The directive goes on the declaration of whichever name the Marshaler warning names, so an alias that is itself a marshal-method receiver (`type SA = Status; func (SA) MarshalJSON()`) accepts it.
- **Placement.** The doc comment of a package-level type declaration: of an ungrouped `type X …`, or of one type inside a `type ( … )` group. A doc comment above a whole group applies to no type and warns "has no effect, place it on a type inside the group". A `schema` directive anywhere else, such as above a route registration or above a type declared inside a function body, is a Detached directive, as is a route directive in a type's doc comment. Placement is judged per directive name, not per comment group: when one group holds a route directive and a `schema` directive, the correctly placed one applies and the misplaced one is reported as a Detached directive.
- **Build-tagged duplicates.** Among declarations of the same name in one package, a declaration without the directive states nothing. Exactly one distinct Stated schema applies; two different ones warn, and the type falls back to `{}` with its Marshaler warning.
- **Repeated directives.** One rule covers every directive name repeated in one comment group. A list directive (`errors`) takes the union of its values, and a flag (`public`) is idempotent. A single-valued directive (`meta`, `schema`) repeated with the same value is deduplicated silently; with different values it warns and neither applies, so the output is what it would be without those lines, as with build-tagged declarations that state different schemas. The same value means the same type word and format for `schema`, and the same resolved type for `meta`; a line that is invalid on its own warns for that and takes no part in the comparison. This rule spans every directive; it is recorded here because `meta` uses the existing route-directive placement and gets no ADR of its own.

## Considered options

- A struct tag on the field. It cannot reach a `Result[T]` payload or a request type itself.
- A project-level mapping (CLI flag or config file). It also reaches types from other modules, but adds a configuration surface. It stays the candidate for those types, as a separate future issue.
- Two schemas, one per direction. More precise for a type that only encodes or only decodes through its methods, but one schema with a README caveat was preferred.
- Also accepting `object`, giving a bare `{type: object}`. Cheap, but it silences the warning without describing the payload.
- Refusing the directive only on a type whose marshal methods are all on its pointer, ADR 0002's pointer-only rule. A type with a value-receiver `MarshalText` and a pointer-receiver `MarshalJSON` would then accept it, though `encoding/json` writes that type through `MarshalJSON` where the value is addressable and through `MarshalText` elsewhere, so one Stated schema would still be wrong at some positions.
- Applying the Stated schema at the explicit `*T` positions of a type with a pointer-receiver encode method. Correct there, since the value is addressable, but only as part of a general rule giving every such in-module type its wire form at `*T`, which would change existing output (a `*PT` with a pointer-only `MarshalText` would go from `{}` to `string`); that rule is left to its own issue.
- Applying a directive on a generic type declaration to every Instantiation. It is right only when the wire form does not depend on the type argument, and for a generic Marshaler type it usually does, so it would state a wrong schema for some Instantiations and silence the warning that would have flagged them.
- Leaving generic types to a follow-up issue. What the directive did on a generic type would then depend on which of #114 and #117 landed first, and could change again when the follow-up decided, under directives projects had already written.

## Consequences

- Hard to reverse: projects write the directive into their source, and the emitted schema is part of the generated output's shape, a declared SemVer surface (`RELEASING.md`).
- One schema is trusted for both directions, so it can be wrong for an encode-only or decode-only type. The README will state that caveat.
- Types from other modules (`decimal.Decimal`) are out of scope: a directive cannot reach a foreign declaration. They keep today's untyped `{type: object}` and its "resolves to no schema" warning until a project-level mapping exists.
